# DESIGN_A — the flat event log

**Stance:** Facts are one flat, immutable, append-only sequence of typed events with rich fields; there is no stored node graph — views, trees, dimensions and drills are all queries over the log, and a "view" is a saved (filter, metric) preset.

## 1. The data model

One artifact per aggregation run: an ordered fact log, loaded as `{fact_id: fact}` — exactly the shape the ported engine already consumes. `lib_drill` never needed a node graph: `resolve_path` derives a node's members by filtering, `discover_dimensions` derives the axes from the facts' own fields via `flatten()`. v1 bolted a registered view/tree layer onto an engine that is already a query engine; v2 deletes the bolt-on and keeps the engine byte-identical.

**Fact kinds** (typed events): `generation` (one per merged `message.id`), `tool_call` (per `tool_use` block), `tool_result` (per `tool_result` block), `user_text`, `metadata` (the bookkeeping record types — no identity granted, empty metrics bag on purpose), `attribution_residual` (synthetic, §2 step 7), `anomaly` (unparseable line: counted and located, never silently skipped).

**Fields:** every fact carries `fact_id`, `kind`, `lane` (the transcript file — the scope of the occupancy carry), `seq` (position in the lane's deduped event order), and `locator` {`file`, `line` (physical, recorded at read time — the Nth parsed record is not raw line N), `line_end`; on generations also `constituent_uuids` + `constituent_lines`, the lossless span PHASE0 §2 requires, since metadata interleaves inside a generation's physical run and drops all-records contiguity to 86.54%}. Identity fields where the raw data carries them: `uuid`, `message_id`, `tool_use_id` (on tool_call AND tool_result — 100%/100% present and resolvable in PHASE0 §1; v1's 0-of-5,911 was pure parse-time loss), `session_id`, `agent_id`, `subagent_info.*`, and `tool_name` (joined onto each tool_result at parse from the earlier matching tool_use in the same file — the join is total, no fallback path). Contributor facts carry `feeds_gen`: the `gen_seq` of the next usage-carrying generation in their lane — interval membership as a plain field, so "the interval" is an equality filter and a free drillable dimension, not a table.

**Metrics** live in a per-fact bag, declared once in `sa_schema.AGGREGATION`/`METRIC_UNITS` (ported verbatim; one module = one declaration site; a derivation test asserts the two dicts' key sets coincide, failing closed on drift). `spend`, `context_delta`, `context_tokens`, `output_tokens` on generation facts only; `observed_chars` on content-bearing facts; `context_added` (new, additive, unit "attributed occupancy tokens") written by the attribution pass.

**Ingest** (a pure function of the file bytes): read with physical line numbers, skip-and-count unparseable (2 in 228,738 on the live corpus); normalize string-vs-blocklist `message.content`; within-file uuid dedup (0.19%); forest-level cross-file uuid dedup at the aggregation boundary (1.35% of distinct uuids are multi-file; never content-keyed, per the ruling); group assistant records by `message.id` and `max_merge_usage` field-wise (80.5% of ids split, 73.0% of those disagree on `output_tokens`); compute `usage_context`, `context_delta` against the SAME lane's previous usage-carrying call (carry resets per file; a usage-less generation gets absent metrics and an unmoved carry — divergence #1), `usage_spend` with per-call tier weights; emit facts in lane order; run the attribution pass. Unknown record types are tolerated, typed `metadata`, granted no identity.

**Queries, not views.** A query = (filter over fact fields) x (declared metric) x (optional drill path); `resolve_path`/`discover_dimensions` execute it. A preset is one dict entry naming a query ("context" → metric `context_added`; "spend" → kind generation, metric `spend`). Adding a metric touches the schema module once; adding a dimension touches zero declarations — `flatten()` discovers fields. Cross-slice pivots are one changed filter or dimension, because nothing was materialized in the old slice's shape. The presentation layer enumerates nothing: units come from `metric_units`, statistic identity from the result record's own `statistic`/`dist_basis` fields, and populations from computed reason-code counts — which kills v1's hand-written denominator prose; the denominator becomes a measurement.

## 2. The attribution walkthrough (raw records → "this tool result added N tokens")

Worked over one lane L = one transcript file in forest F. Every field is named; corpus figures are PHASE0's (population: 1,845 files / 228,738 records, measured 2026-07-28).

1. **Raw.** Line 41 of L: assistant record, `uuid` u9, `message.id` m7, content `[tool_use {id: tu_42, name: "Read", ...}]`, `message.usage` {input_tokens 4, cache_read_input_tokens 8120, cache_creation_input_tokens 80, output_tokens 310}. Line 42: user record, `uuid` u10, content `[{type: "tool_result", tool_use_id: tu_42, content: <9,400 chars>}]`. Line 43: an attachment record (no uuid — pure bookkeeping; carries no tokens, PHASE0 §4). Lines 44–45: two assistant records sharing `message.id` m8 with disagreeing usage snapshots.
2. **Merge.** m8's records max-merge (`max_merge_usage`, recursing into nested `cache_creation`) into one generation fact G8: `message_id` m8, `gen_seq` 8, `locator.constituent_uuids` [u11, u12], `constituent_lines` [44, 45], `metrics.context_tokens = usage_context = 4 + 17650 + 96 = 17750`. m7 → G7: `context_tokens` 8204, `metrics.output_tokens` 310, `metrics.spend = 1.0*4 + 0.1*8120 + 1.25*80 = 916.0` (tier read per call from nested `cache_creation`; 5m here).
3. **Delta.** `G8.metrics.context_delta = usage_context(G8) − usage_context(G7) = 17750 − 8204 = +9546` — signed, unclamped.
4. **Interval.** Contributors of G8 = facts with `lane == L` and `feeds_gen == 8`, kinds tool_result/user_text (metadata excluded: every uuid-less type is token-free bookkeeping, and 0 of 65,470 user records lack a uuid — every token-relevant contributor is identifiable, PHASE0 §4). Here: exactly one — tool_result fact T: `uuid` u10, `tool_use_id` tu_42, `tool_name` "Read", `observed_chars` 9400. 84.43% of 51,933 intervals on this corpus have exactly one contributor; zero have none.
5. **Subtract-then-split.** Feed-forward term = `G7.metrics.output_tokens` = 310 (`Δocc ≥ output(N−1)` on 97.79% of 45,555 pairs). Write `G7.metrics.context_added = 310` — the model's own reply entering the window. Remainder R = 9546 − 310 = 9236.
6. **Exact assignment.** One contributor, so `T.metrics.context_added = 9236` — exact, no estimator. The answer: *tool_result u10 (Read, tu_42) added 9,236 tokens to lane L's window*, and `T.locator.file`:`T.locator.line` opens the evidence line. (9,236 tokens against 9,400 chars: the implied ratio is data, never a model — chars stay rejected as an estimator; the measured spread is p10 0.361 / p90 0.640.)
7. **Every other case is a NAMED bucket**, one `attribution_residual` fact per interval carrying `feeds_gen`, `reason`, `candidates` (fact_ids), `metrics.context_added = R`:
   - `multi_contributor` (~15.6% here; ~23% on the contract's corpus): candidates named, measured total kept, never spread.
   - `feedforward_exceeds_delta` (≤2.21%): R < 0 though Δocc ≥ 0; nothing exact to say.
   - `lane_head` (`gen_seq` 0, previous = None): Δocc is the whole boot prompt; the visible user text did not add those 8,204 tokens — boot did. Never labeled exact.
   - `interleaved` (84 of 53,855 message.ids): interval order ill-defined; routed here and counted.
   - `shrink` (Δocc < 0): quarantined, not attributed; the signed delta stays on the generation (never clamped), and no `context_added` mass is emitted.
8. **Invariants, testable:** for every non-quarantined interval, Σ`context_added` (contributor + feed-forward + residual) equals that generation's `context_delta`; per lane, Σ`context_delta` telescopes to final occupancy. Every headline prints computed populations — "exact over A of N intervals; ambiguous B (T tokens); lane-head C; shrunk D" — from reason codes, not prose claims.

The walk completes. It also dissolves the tree inversion for the attributed majority: the injected content that is ~95% of observed chars and carried zero token mass in v1 now carries exact token mass on the very facts a drill reaches (`tool_name`, `subagent_info`, `locator.source` are all present on them), and where it cannot, the residual is a visible row no bounded table may drop.

## 3. Divergence from v1's [OPEN] choices

1. **Usage-less call emits absent metrics, not 0** (§6 parenthetical). `0` is a claim of measured no-growth; absent is the truth. `_metric` already sums absence as nothing, so totals are identical, and `n_valued` then reports honestly. Decision-log entry; lands only on ruling.
2. **Attribution rules (§4, all [OPEN]): adopted with refinements.** Subtract-then-split kept. ONE residual bucket kept in every total, but carrying machine-readable `reason` codes as annotation; lane-head and interleaved intervals are routed there rather than mislabeled exact.
3. **Chars: stay rejected** — not even published-with-band in build v1 (the no-estimates non-negotiable governs).
4. **Everything else kept as ported:** score = stat x cover, cover as a fact count, missing-key/null unified into one residual, statistic-scoped fields absent not defaulted, unclassified metric raises, max-merge, the purity boundary, derivation-plus-vacuity-guard testing. No new measurement, so no challenge — and the flat log is the engine's native input, so the mutation-tested asset needs zero edits.
5. **Declared deviation from my own stance:** attribution is computed at INGEST and written into fact fields, not re-derived per query. Pure read-time derivation would recompute adjacent-record arithmetic on every query for no gain; writing it once keeps queries as filters and the log immutable (re-ingest regenerates). This is where evidence bent the assigned stance.

## 4. Deliberately not building

TIME/scheduling (timestamps are ordinary fact fields, so time metrics are later declarations, not a redesign); any estimator (chars, spreads, ratios-as-predictors); window naming across files (windows span files but no marker exists — peaks stay per-lane and say so); cross-file replayed-usage verification (PHASE0 flags it unverified; dedup keeps first occurrence and counts drops); dollars; the HTML/JS twin, parity harness, view registration tables, and per-view denominator prose; live monitoring; any grading of conversation content.

## Suspected misfiles

1. **§6 "the carry resets at the start of EVERY file" [ARITHMETIC].** The arithmetic half is only "never difference occupancies of unrelated windows". Choosing the FILE as the lane is a modeling choice: a window is not a file [MEASURED], continuations continue one window, and the per-file reset manufactures a boot-sized delta at every continuation head. My `lane_head` bucket absorbs that honestly, but the reset itself deserves [OPEN]/[RULING] so a future window-stitching design is not refused as a category error.
2. **§4 negative-delta quarantine leads [ARITHMETIC]** while its own trailing parenthetical says quarantine-vs-signed-axis is [OPEN]. The arithmetic covers only "after a shrink, increments stop summing to the level"; the disposition is a choice.
3. **§5 "spend/context_delta exist ONLY on generation facts" [ARITHMETIC].** The denominator-inflation argument is real, but which kinds carry which metrics is schema design (RULING-shaped). My `context_added` on tool_result facts is legitimate only because the invariant is metric-specific; the ARITHMETIC tag invites over-generalizing it into "non-generation facts may carry no token metrics", which would forbid exact attribution itself.

## What I'd attack in the obvious design

The obvious v2 is a star schema: an interval TABLE, an attribution edge table, materialized per-view trees. Attack: every stored join duplicates what position in the log already encodes, and can drift from the log with no test that notices — v1's hand-written denominator strings are exactly this disease. A materialized tree freezes one hierarchy precisely where PURPOSE says the biggest lever lives on a different slice. Registered views recreate the 40-table surface (three fail-silent) the design gates exist to kill. If a design's "add a dimension" story touches more than zero declarations, it has already lost to `flatten()`.

## Weakest point

The interval edge cases are where I expect critics to land — rightly, because they are where this domain mints its signature failure, the confident wrong number. `feeds_gen` is defined over the deduped lane order: a replayed record dropped by dedup, an interleaved generation, or a continuation head each shifts what "between" means, and a bug there produces an EXACT-labeled attribution that is exactly wrong. The mitigations are the reason-code buckets, the per-interval sum invariant, and the telescoping test — but the honest statement is that the 84.43% exact rate was measured over cleanly-ordered intervals, and my routing of every ill-ordered case into the residual is asserted by design, not yet verified by a probe over the live corpus. A second seam: ingest-time enrichment softens the stance itself, and a critic can fairly ask whether a "flat log" whose ingest writes derived fields is one artifact or two.
